# M12e: dropper-shaft connectors and a fourth, nether-themed layer

## What shipped

- `CavePlanner.LAYERS` is now 4. The new layer's band (-92..-68) sits 10 blocks
  of solid separator rock below Chaos Depths' own band (-58..-30), reusing the
  exact per-layer `Spec` pattern the other three layers already use.
- The mine dimension's height was extended downward (`min_y` -64 -> -160,
  `height` 384 -> 480) to make room; the world's top (y=319) is unchanged, so
  the hub, surface exit, and every existing layer keep their exact coordinates.
- `Rock.MIN_Y` (the ore/landmark eligibility floor) was extended from -58 to
  -100 to cover the new layer.
- `CaveTerrain.ores()` now builds one ore table per `CavePlanner.LAYERS`
  layer instead of one per `OreCatalog.Tier`; the new layer reuses Chaos
  Depths' own ore table (quartz, ancient debris, diamond, emerald, etc.) -
  the "nether theme" is delivered as ore/content identity, not a new rock
  palette (see Non-goals below for why).
- One additional "dropper" connector per layer pair - a straight vertical
  fall chute, distinct from the three existing walkable-ramp descents - at
  roughly 1000/2000/3000 blocks straight-line from the hub for the
  hub->layer1, layer1->layer2, and layer2->layer3 transitions respectively.
  Each has a shallow water landing (fall-damage-safe) at the bottom.
  Best-effort: the three main descents already guarantee connectivity on
  their own, so a layer pair where no clean dropper column is found simply
  doesn't get one, never a generation failure.

## The two blockers from the original deferral, and how each was resolved

1. **Old v1 `TopologyProfile.validate()` requires exactly upper/middle/chaos.**
   Turned out not to block this work at all: that validation only governs
   `topology_profiles/standard.json`, a file the live v2 cave-generation path
   (`RunSeedNoiseLevelSource` -> `CaveTerrain`) never consults for its own
   layer count. `CavePlanner.LAYERS` is an independent constant. No change to
   the v1 topology schema was needed or made.
2. **`CaveStack.planOnce`'s descent-building loop is tightly coupled.**
   Also turned out to be a non-issue for the *main* descents: that loop
   already iterates generically over `CavePlanner.LAYERS` (it was never
   hardcoded to 3), so bumping the constant was enough for the three main
   descents to extend automatically to the new layer pair with zero changes
   to `chooseTops`/`buildDescent`/`excludeAlong`. The dropper shafts needed
   genuinely new code, but it was added as a separate, additive post-process
   step after the existing loop finishes, not a modification to it - the
   existing algorithm's own invariants were never touched.

## A real bug found and fixed during this work

The first dropper implementation made every step of the shaft share the same
(x,z) column (correct for a vertical shaft) and reused `buildTubeColumns`'
existing per-step span logic unchanged. That logic also carves a 3-wide
*lateral* band at each step, and for a stationary column it always treats X
as the lateral axis (since x never changes between consecutive steps). Once
merged across all of a shaft's steps, that lateral band swallows the solid
floor plate the entrance waypoint needs to stand on - confirmed by
`CaveStackTest`'s own census-walker check, which correctly flagged the
dropper's top waypoint as unreachable. Fixed by giving the entrance a
one-block *Z*-offset approach tile (never the shaft's own lateral axis), so
the player's standing tile is a distinct column the shaft's spread never
touches. Full root-cause and fix are in `CaveStack.buildDropper`/
`approachTile`'s javadoc.

## Non-goals (explicitly not attempted here)

- **No custom rock palette for the new layer.** The base rock block at any Y
  comes from the dimension's own underlying noise generator, not from a
  region-keyed palette function in this codebase (the only such function,
  `MineGenerator.regionForY`-driven palette selection, belongs to the old v1
  segment-writer path and was not confirmed to be live in the v2 pipeline).
  Adding netherrack/basalt specifically for this layer would mean writing new
  per-chunk palette logic without being able to verify which generation path
  actually owns block materials for the live mine - safer to defer than guess.
- **Dropper shafts have no ladders.** Only the water landing was implemented.
  Climbing back out requires using one of the three main descents or another
  dropper; this is a one-way fast route down, not a two-way shaft. Ladders
  would need new per-block wall-placement logic in `CaveTerrain.carve`
  keyed off descent type, which was out of scope for this pass.
- **No deployment migration tooling.** Changing the dimension's `min_y`/
  `height` is safe for a brand-new world, but this mod's mine dimension is
  entirely procedural and already fully regenerated by the existing daily
  reset system - there is no persistent player-built content inside it to
  migrate. Deploying this to a server with an already-generated mine requires
  deleting that dimension's region files (or running a fresh daily reset)
  once, the same way any other generation-affecting change in this project's
  history has required a reset. This is noted here, not automated.
